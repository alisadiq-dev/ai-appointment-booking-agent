# Google Calendar

The business calendar is accessed as a **service account** that the calendar is shared with.
There is no OAuth user flow and no domain-wide delegation.

## How bookings use the calendar

Calendar sync is **strict**: the booking and its calendar entry succeed or fail together.

| Operation | Order inside the request | If Google fails |
|---|---|---|
| Create | validate, check manual calendar events (409 if one overlaps), insert the booking row (takes the write lock; the row already carries `google_event_id`), create the event | `503 calendar_unavailable`; the request transaction rolls the row back |
| Reschedule | validate, check manual events, update the row, patch the event | `503`, rolled back. If the event was deleted by hand: `409 calendar_event_missing` (cancel it and book again), rolled back |
| Cancel | mark the row cancelled, delete the event (already gone counts as success) | `503`, rolled back: the booking stays confirmed, so retry later |
| Availability | database bookings plus manual calendar events | `503` (fails closed; a closed day needs no Google call) |

- **Rollback** is the app's per-request database connection: any exception rolls the request's
  changes back, and the response is only sent after the commit (`Depends(scope="function")`).
  `BookingService` never commits itself, so it must run inside such a request.
- **Database first, Google last.** A database conflict (`409 slot_unavailable`) never reaches
  Google. The booking id is generated by the service, so the row carries the event id before the
  event exists.
- **Event content:** title `"<service> - <customer name>"` (`Customer` when the profile has no
  name), description `Booking <booking id>`, and the booking id plus `source=ai-appointment-agent`
  in private extended properties. No email, phone or attendees (the event type has no field for
  them).
- **Manual events block time.** Anything added to the calendar by hand (a dentist visit, a
  holiday) removes those slots from availability and rejects bookings that overlap it. Events
  this app created are ignored for this (the bookings table already covers them), as are
  cancelled events and events marked *free*.
- **Recurring events** are expanded (`singleEvents=true`), so every occurrence blocks time, not
  just the first.
- **Paging:** `list_busy` follows `nextPageToken` until the list ends. If it ever needs more
  than 20 pages it fails closed instead of answering from a partial view.
- **All-day events block the whole local day.** The date is read in `BUSINESS_TIMEZONE`, not
  UTC (for example `2031-03-05` in Karachi is `2031-03-04T19:00Z` to `2031-03-05T19:00Z`), and a
  DST change day is its real 23 or 25 hours. A multi-day event blocks each of its days.
- **Local dev:** with `CALENDAR_ENABLED=false` a no-op calendar is used (nothing is synced) and
  startup logs a warning. This must be `true` in production. With it `true`, the Google client is
  built at startup, so a bad key stops the app from starting.
- **Known limit:** if the database commit itself fails after Google accepted a create, an
  orphan event remains. It carries the booking id in its private properties for cleanup. The
  window is the commit alone, because every earlier failure rolls back before Google is called.

## Adapter behaviour (`app/integrations/google_calendar.py`)

- **Interface:** `CalendarPort` (`app/services/ports.py`). Tests mock the HTTP layer or use a
  `FakeCalendar`, so no credentials are needed.
- **Scope:** `https://www.googleapis.com/auth/calendar.events` only (create, patch, delete and
  list events; no calendar settings or sharing).
- **Event ids:** the booking UUID in hex. Google accepts only `a-v` and `0-9` in custom ids
  (5 to 1024 characters), which hex satisfies.
- **No attendees:** Google requires domain-wide delegation for a service account to invite
  attendees, so customer details go in the event title and description instead.
- **Retries:** each call has a timeout (`CALENDAR_TIMEOUT_SECONDS`) and retries `5xx`, `429`
  and `403 rateLimitExceeded` with exponential backoff (`CALENDAR_NUM_RETRIES`).
- **Fail closed:** when retries run out, the adapter raises `CalendarUnavailableError`
  (`503 calendar_unavailable`) and logs the status, never credentials or identifiers.
- `httplib2` is not thread-safe, so each thread builds its own client.

## Verified against the real API (live test findings)

The live tests ran against a real calendar (4 of 4 pass, nothing left behind). They disproved
two assumptions that the mocked tests had baked in. Both are now handled and unit-tested.

**1. Deleted events are "cancelled" tombstones, and patching one does not fail.**

- After `events.delete`, the event is still readable by id with `status: "cancelled"`.
- `events.patch` on it answers **`200`** (not `404`/`410`) and leaves it `cancelled`: it is not
  revived, but the times of the tombstone change.
- So `update_event` checks the returned status: `cancelled` raises `CalendarEventNotFoundError`,
  which the service turns into `409 calendar_event_missing`. Relying on a 404 would have let a
  reschedule "succeed" against an event nobody can see.
- Deleting twice is fine (`404`/`410` count as success).

**2. A deleted event's id can never be reused: creating it again answers `409`.**

- `events.insert` with the id of a tombstone returns `409 The requested identifier already
  exists`, indistinguishable from "the first attempt actually succeeded".
- Treating every 409 as "already created" would therefore report success for an event that does
  not exist. After a 409 the adapter now **reads the event**: `confirmed` means the earlier
  attempt worked (a retried create, safe and idempotent); `cancelled` fails closed with
  `503 calendar_unavailable` and an error log line.
- This cannot trap a customer: a booking id is generated once per attempt, so a fresh attempt
  uses a fresh id and a fresh event.

Other facts confirmed live: events keep the private `source` and `booking_id` properties and the
`Asia/Karachi` time zone; no `attendees` are added; manual, free, app-created and all-day events
are classified correctly by `list_busy`; a calendar that is not shared returns `404` and the log
says to check the sharing.

## One-time setup

1. In Google Cloud, create or pick a project and **enable the Google Calendar API**.
2. Create a **service account** (no IAM roles needed) and download a **JSON key**. Store it
   outside the repository, for example `~/.secrets/`, mode `600`.
3. In Google Calendar, create a **dedicated calendar** (not the account's primary one).
   *Settings and sharing, Share with specific people*: add the service account's email (the
   `client_email` field in the key file) with permission **Make changes to events**.
4. Copy the **Calendar ID** from *Settings and sharing, Integrate calendar*. It usually ends in
   `@group.calendar.google.com`. The service account's own `primary` calendar is empty, so use
   the explicit id.
5. Put the values in an env file that is **not in the repo**:

   ```bash
   # ~/.secrets/booking-agent.env   (chmod 600)
   export CALENDAR_ENABLED=true
   export GOOGLE_CALENDAR_ID='...@group.calendar.google.com'
   export GOOGLE_SERVICE_ACCOUNT_JSON='{"type":"service_account", ...one line...}'
   ```

   On SnapDeploy, set the same variables as environment variables in the dashboard (see
   [deploy.md](deploy.md)). With `CALENDAR_ENABLED=true`, the
   app refuses to start if the id or key is missing or the key is not valid service account JSON.

## Live tests

`tests/integration/test_google_calendar_live.py` talks to the real API. It is skipped unless
`GOOGLE_CALENDAR_ID` and `GOOGLE_SERVICE_ACCOUNT_JSON` are set, and **fails** instead when
`REQUIRE_DB=1` (see [local-supabase.md](local-supabase.md)).

```bash
source ~/.secrets/booking-agent.env && uv run pytest -m live_google -v -s --no-cov
```

Safety: everything it creates lives in March to April 2031 and has a summary starting with
`LIVE TEST`. Each test deletes what it made, and a fixture sweeps that window before and after
and asserts nothing is left (it prints `LIVE-CLEANUP: stale_before=… swept_at_end=…
leftover_after=…`). Events outside that window, or without that prefix, are never touched. Use a
dedicated test calendar anyway.

## Troubleshooting

| Symptom | Likely cause |
|---|---|
| `404 notFound` on the calendar, and the service account sees **0 calendars** | The calendar is not shared with the service account (check the email matches `client_email`), or `GOOGLE_CALENDAR_ID` is for a different calendar. Sharing takes effect immediately; no acceptance step. |
| `403 forbidden` / `insufficientPermissions` | Shared with *See all event details* only. Change it to **Make changes to events**. |
| `403 accessNotConfigured` | The Calendar API is not enabled in the key's project. |
| `401` / `invalid_grant` | Key deleted or disabled, or the machine clock is far off. |
| `403 rateLimitExceeded` / `429` | Retried automatically with backoff; if it persists you will see `503 calendar_unavailable`. |

The log lines name the failing operation and HTTP status, and point at sharing for `403`/`404`,
but never print the calendar id, the service account email or any key material.

## Secrets rules

Never commit, paste or log the key file, `GOOGLE_SERVICE_ACCOUNT_JSON` or the calendar id.
Settings hold them as `SecretStr` and set `hide_input_in_errors`, so validation errors and
reprs do not echo them (tests assert this). `.gitignore` blocks `.secrets/`, `*.pem` and
`service-account*.json`.
